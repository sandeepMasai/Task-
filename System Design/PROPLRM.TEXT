# Food Delivery Platform System Design

## Design Similar to Swiggy / Zomato

---

# Assumptions

1. Daily Active Users (DAU) = 5 Million
2. Peak Orders = 5,000 Orders/sec
3. Average Menu Size = 50 Items per Restaurant
4. Total Restaurants = 1 Million
5. Average Order Size = 5 Items
6. Average Order Record Size = 2 KB
7. Average Menu Item Size = 1 KB
8. Availability Target = 99.9%
9. Read/Write Ratio = 80:20
10. Real-time updates required within 2 seconds

---

# Part 1 – Capacity Estimation

## 1. Restaurant & Menu Storage

### Restaurant Data

Assume:

* 1 Million Restaurants
* Restaurant Metadata = 2 KB

Storage:

1,000,000 × 2 KB

= 2 GB

---

### Menu Data

Assume:

* 50 Menu Items per Restaurant
* 1 KB per Menu Item

Total Menu Items:

1,000,000 × 50

= 50 Million Menu Items

Storage:

50,000,000 × 1 KB

= 50 GB

---

### Total Storage

Restaurants = 2 GB

Menus = 50 GB

Total = 52 GB

Considering Replication (3x):

52 × 3

= 156 GB

---

## 2. Order Service QPS

Peak Orders:

5,000 Orders/sec

Each Order Generates:

1 Create Order Write

1 Payment Update

5 Status Updates

1 Delivery Assignment

Total Writes:

5,000 × 8

= 40,000 Writes/sec

---

Read Traffic

Read/Write Ratio = 80:20

Reads:

40,000 × 4

= 160,000 Reads/sec

---

Final Estimate

Read QPS ≈ 160K/sec

Write QPS ≈ 40K/sec

---

## 3. Bandwidth Requirement

Assume:

Order Payload = 2 KB

Peak Orders = 5,000/sec

Bandwidth:

5,000 × 2 KB

= 10 MB/sec

Status Updates:

25,000 Updates/sec

Payload = 1 KB

25 MB/sec

Total:

≈ 35 MB/sec

≈ 280 Mbps

Provision:

1–2 Gbps Capacity

## Delivery Partner Assignment

Flow:

1. Order Created

2. Event Published to Kafka

3. Delivery Service Consumes Event

4. Query Nearby Delivery Partners

5. Rank by:

   * Distance
   * Availability
   * Current Load

6. Send Assignment Request

7. First Acceptance Wins

8. Update Order

---

## If No Delivery Partner Available

Order enters:

WAITING_FOR_PARTNER

Retry Strategy:

Retry every 30 seconds

Expand Search Radius

Offer Incentives

Escalate to Backup Fleet

Notify Customer

If timeout exceeds threshold:

Order Cancelled + Refund

# Part 5 – Failure Scenarios

## Scenario 1

Delivery Partner App Goes Offline

Detection:

Heartbeat Missing

GPS Updates Stop

Actions:

1. Mark Driver Offline
2. Notify Customer
3. Reassign Driver
4. Escalate to Operations Team

Order Status Maintained

No Data Loss Through Kafka Events

---

## Scenario 2

Payment Service Unavailable

Detection:

Gateway Timeout

Actions:

1. Order Stored as PENDING_PAYMENT
2. Retry Payment
3. Queue Retry Event
4. Notify Customer

If Retry Succeeds:

Continue Workflow

If Retry Fails:

Cancel Order

No Duplicate Orders Through Idempotency Keys
